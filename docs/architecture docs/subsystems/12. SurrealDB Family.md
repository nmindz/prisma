# SurrealDB Family

## Overview

SurrealDB is a multi-model database. One deployment stores documents, walks
graph edges, resolves record links, and answers approximate-nearest-neighbour
queries over vectors, and its query language — SurrealQL — reaches all four.
That is why SurrealDB lands as its own family alongside `sql` and `mongo`
rather than as a dialect of either.

## At a glance

| | |
| --- | --- |
| Family id | `surreal` |
| Target id | `surrealdb` |
| Transport | WebSocket RPC (`/rpc`), `json` subprotocol |
| Server floor | SurrealDB v3.2.4 |
| Public facade | `@internal/extension-surrealdb` → `surrealdb({ … })` |

## SurrealQL is not SQL

The temptation is to treat SurrealQL as a SQL dialect and reuse the SQL
family's AST and lanes. That was tried and rejected: the overlap is shallower
than the syntax suggests, and the mismatch shows up as a long list of
constructs the SQL lanes can build but SurrealDB refuses to run.

Every row below is how SurrealDB v3.2.4 actually behaves:

| SQL construct | SurrealQL |
| --- | --- |
| `JOIN` | Does not exist. Relationships are `record<>` links or graph edges |
| `OFFSET n` | `START n` |
| `HAVING` | Does not exist. Filter an outer `SELECT` instead |
| `SELECT DISTINCT` | Not a keyword |
| `RETURNING` | `RETURN`, with `BEFORE` / `AFTER` / `DIFF` / `NONE` |
| `PARALLEL` | Removed from `SELECT` in v3 |
| `CASE … END` | `IF … THEN … ELSE … END` |
| `CAST(x AS t)` | `<t> x` |

And several rules have no SQL analogue at all:

- **`ORDER BY` sorts over the projection.** Ordering by a field the `SELECT`
  does not return fails to parse: *Missing order idiom `age` in statement
  selection*.
- **A record id's key is a parser token, not an expression.** `person:$id`
  fails; SurrealDB says so and names the remedy — *Record-id's can be created
  from a param with `type::record("person", $id)`*.
- **`option<T>` means `NONE | T`, not `NULL | T`.** Writing JS `null` into an
  `option<decimal>` is rejected outright.
- **The bare `<|k|>` KNN operator was removed in v3.** An operand is required:
  `<|k, EF|>` against an HNSW index, or `<|k, DISTANCE|>` for a brute-force
  scan.

These are encoded in the types where possible — `KnnOperand` is non-optional,
`RecordIdKey` is its own union — so a builder cannot express a query the
database would reject.

## How the four models are represented

| Model | Representation |
| --- | --- |
| Document | `SurrealTable` with `tableType: { kind: 'normal' }` |
| Graph | `SurrealTable` with `tableType: { kind: 'relation', from, to }`; `RELATE` writes into it, `->edge->` walks it |
| Relational | A `SurrealField` typed `record<other>` — the link that stands in for a foreign key |
| Vector | A `SurrealIndex` with the `hnsw` variant, queried with `<|k,DIST|>` |
| Full-text | A `SurrealIndex` with the `fulltext` variant, over a `DEFINE ANALYZER` |

A graph edge is a record in its own right: SurrealDB fills `in` and `out` from
the endpoints of a `RELATE` and lets the edge carry properties of its own. So
an edge table is a table like any other, and lives in the same entity kind
rather than in a parallel concept.

## Two lanes to build a query

`db.orm` is not the only way to produce a plan. `@internal/surreal-query-builder`
is a second, contract-free lane — `selectFrom`, `createInto`, `upsertRecord`,
`updateWhere`, `deleteWhere`, `relate`, and a set of DDL builders
(`defineTable`, `defineField`, `defineIndex`, and their `remove*`
counterparts) — published as the `query-builder` subpath of both
`@prisma/orm-family-surreal` and `@prisma/orm-surrealdb`, next to the
collection lane itself.

The collection lane reads a contract for table and field declarations, so it
can validate a `where` key, match a unique index, or classify a field's type
before compiling. The query builder has no contract behind it: a caller
states the table and shape directly, trading that validation for not needing
a generated contract in hand — a migration script, a one-off tool, or a test
fixture is the usual reason to reach for it instead. Both lanes compile to
the same `SurrealQueryPlan`, and neither executes anything on its own.

Neither lane offers a predicate-shaped `UPSERT` (`UPSERT table WHERE …`):
SurrealDB's own predicate form creates a fresh, randomly-keyed record for
every row the predicate matches nothing, which is rarely what a caller
reaching for upsert-by-key wants. The collection lane's `upsert` instead
takes either a record id or a `where` naming exactly one declared unique
index; the query builder's `upsertRecord` takes only a record id, since it
has no unique-index declarations to match against.

## Building a context without a connection

`surrealdbStatic({ contractJson })`, from `@prisma/orm-surrealdb/static`,
assembles the same context, collection lane, and raw lane `surrealdb(...)`
does, but with no driver in the execution stack — nothing to connect, and
nothing to close. It exists for the same reason the query builder does:
compiling and inspecting `SurrealQueryPlan`s without a live database, useful
for a tool that only needs to render SurrealQL or validate a contract's
shape. `db.orm` and `db.surql` behave identically whether the stack came
from `surrealdbStatic` or a connected client, because neither reads from the
stack's driver to compile a plan.

## The wire: CBOR by default, JSON on request

SurrealDB's websocket offers two subprotocols, and they are not equivalent.

Under `json` a `datetime`, a `decimal`, a `duration` and a `uuid` are all just
strings, `bytes` is an array of numbers, a record id is text that has to be
split on a colon, and — the loss no workaround recovers — `NONE` and `NULL`
are both `null`. Sending a value back untyped fails, and SurrealDB says so:

```
Couldn't coerce value for field `amount`: Expected `decimal` but found `'12.34'`
```

Under `cbor` each type has its own tag. `@internal/surreal-cbor` implements
the encoding with no dependency; every tag number in it is what SurrealDB
v3.2.4 itself puts on the wire:

| Tag | Type | Payload |
| --- | --- | --- |
| 6 | `NONE` | null |
| 7 | table name | text |
| 8 | record id | `[table, id]` |
| 10 | `decimal` | text |
| 12 | `datetime` | `[seconds, nanoseconds]` |
| 14 | `duration` | `[seconds]` or `[seconds, nanoseconds]` |
| 37 | `uuid` | 16 raw bytes |
| 49 | range | `[start, end]`, bounds tagged 50 / 51 |
| 88–94 | geometries | GeoJSON coordinates |

That buys four things JSON cannot give:

- **`NONE` is not `NULL`.** An absent `option<T>` decodes to `undefined` and an
  explicit null to `null`. Under `json` both arrive as `null`.
- **Nanoseconds.** `datetime` carries `[seconds, nanos]`, so an instant keeps
  precision a JS `Date` would round away.
- **Record ids arrive structured**, so nothing parses on a colon.
- **No bind-site casts are needed** — a decimal is already a decimal on the
  wire. (The casts below are still emitted; against a CBOR connection they are
  no-ops, and they are what makes the `json` fallback correct.)

The two JSON mechanisms, both driven by the declared field type:

1. **A cast at the bind site.** `bindCastFor` derives the SurrealQL cast a
   parameter needs, so the lowerer emits `<decimal> $p0` rather than `$p0`.
2. **`NONE` for an absent optional.** `bindsAsNone` recognises a `null` in an
   `option<…>` slot and the lowerer writes the keyword, registering no
   variable — because SurrealDB refuses to cast `NULL` into anything, even
   `<option<datetime>> NULL`.

### The cost, measured

CBOR is the default for correctness, not for speed. Decoding it is a JS loop
where `JSON.parse` is native C++, and that shows. Selecting 500 rows of
`datetime` + `decimal` + `string` through the whole runtime, against a local
server:

| | per query | payload |
| --- | --- | --- |
| `json` | 1.82 ms | 41.8 kB |
| `cbor` | 2.41 ms | 25.3 kB |

So CBOR costs about a third more CPU and moves about 40% fewer bytes — a trade
that inverts as soon as the database is not on localhost. Pass
`protocol: 'json'` to `surrealdb(...)` to choose the other side of it, or when
a proxy cannot pass binary frames.

### Values must not be recognised with `instanceof`

Every package bundles its own copy of `@internal/surreal-value`, so a
`SurrealDatetime` built inside the driver's bundle is not an `instanceof` the
class the caller's bundle exports. Since values cross that boundary on every
query, `instanceof` is unusable. The value model instead carries a brand keyed
by `Symbol.for('prisma.surreal.value.kind')`, which resolves through the
runtime-wide registry and is therefore identical in every copy. The key
deliberately spells no `@internal/*` package name — published shell dists must
not carry internal package names. `surrealKind` reads it, and per-kind guards
(`isRecordId`, `isSurrealDatetime`, …) narrow on it; the CBOR encoder and the
codecs dispatch on it.

## Why WebSocket rather than HTTP

SurrealDB exposes `/rpc` over both HTTP and WebSocket, and the HTTP form is
simpler — stateless, no connection to manage. The driver uses WebSocket anyway,
for one reason: **transactions**. SurrealDB implements `begin` / `commit` /
`cancel` only on the WebSocket protocol; the HTTP RPC answers
`method_not_found` for all three. An interactive transaction, where a read
sees its own uncommitted writes, is reachable no other way.

The transaction id returned by `begin` rides on a `txn` field of each
subsequent request. `acquireConnection` opens a second socket rather than
sharing the driver's, because a transaction is bound to the connection that
opened it.

Node 24 ships a global `WebSocket`, so the driver needs no dependency.

## Result envelopes

A `query` call returns one envelope per statement, and a failing statement
reports `status: 'ERR'` *inside* an otherwise successful call. Every envelope
is validated, not just the one whose rows the caller wanted — a
multi-statement query whose setup failed would otherwise return a
plausible-looking empty result from a statement that never ran.

Payload shape varies: a `SELECT` yields an array, `FROM ONLY` yields one
object, and `RETURN NONE` yields `null`.

`affectedRows` is the number of records returned, because SurrealDB reports no
separate count. A write ending in `RETURN NONE` therefore reports zero.

## Batching

SurrealDB takes several statements in one `query` call, and the round trip is
what dominates once the database is not on localhost. `db.batch` lowers a list
of plans into one request wrapped in `BEGIN` / `COMMIT`:

```ts
const [created, updated, listed] = await db.batch([
  db.orm.person.create({ id: 'ada', data: { name: 'ada', age: 36 } }),
  db.orm.person.update({ id: 'ada', data: { age: 37 }, merge: true }),
  db.orm.person.findUnique('ada'),
]);
```

Two details of v3.2.4's behavior the implementation has to get right:

- **Parameter names collide.** Every plan numbers its own bind sites from
  zero, so two plans would each bind `$p0` to different values. Each plan is
  lowered under its own prefix (`$b0_p0`, `$b1_p0`).
- **`BEGIN` and `COMMIT` take envelopes of their own.** SurrealDB answers with
  one envelope per statement including those two, so plan *n* is not envelope
  *n*; the adapter computes the mapping and sends it with the text.

The transaction wrapper is what makes the batch atomic. A statement that fails
aborts the rest and nothing is written. On the wire every affected envelope
still arrives with `status: "ERR"` — the genuinely failed statement carries
its own error, and the skipped ones say so via `details.kind: "NotExecuted"` —
so the driver's rule is simple: the first `ERR` envelope fails the whole batch
call, and the error names the plan it maps back to.

## Live queries

`LIVE SELECT` is a statement, not a driver call: SurrealDB compiles it like any
other, so the `WHERE` runs server-side against each change and a filtered
subscription costs the client nothing. The statement's result is a
subscription id; the notifications that follow arrive on the same socket as
ordinary replies but carry **no request id**, which is how the RPC client
tells them apart and routes them by live id instead.

```ts
const feed = await db.live(db.orm.ticker.live({ where: { price: { gt: 500 } } }));

const stop = feed.subscribe((change) => {
  change.action; // 'CREATE' | 'UPDATE' | 'DELETE' | 'KILLED'
  change.record; // RecordId
  change.value;  // decoded against the contract, exactly as a row would be
});

for await (const change of feed) { /* … or iterate */ }

await feed.kill();
```

Both consumption styles share one stream. Notifications are buffered when
nobody is iterating yet — a change can land between `LIVE SELECT` returning
and the caller reaching its loop — and the buffer is bounded so a slow
consumer cannot turn a subscription into a leak.

`live` is on `SurrealConnection` and the driver, but deliberately **not** on
`SurrealTransaction`: SurrealDB registers a live query against the session, and
an uncommitted transaction has no session to attach one to. The type system
says so via a separate `SurrealLiveQueryable` interface.

## What the collection lane compiles beyond CRUD

`@internal/surreal-orm`'s README covers this surface in full; the shape of
it matters here because it is what makes the collection lane more than a
thin wrapper over `SELECT`/`CREATE`/`UPDATE`/`DELETE`:

- **`upsert` on a unique key.** Passing `where` instead of `id` looks the
  record up by exactly one declared unique index and branches into
  `UPDATE`/`CREATE` from there, wrapped in its own transaction unless the
  caller says the plan is already going into one.
- **`groupBy` dispatches its aggregate functions by field type** —
  `math::*` for numeric fields, `time::*` for `datetime`, a grouped
  `array::*` form for `string` — and throws rather than emit a lowering
  that would misbehave on a field type it has no verified form for.
- **Relation filters walk or quantify a link.** A nested `where` on a
  to-one relation traverses it; a to-many relation takes `some` / `every` /
  `none`, each compiling to its own verified SurrealQL form.
- **`startsWith` / `endsWith` and `mode: 'insensitive'`** fold both sides of
  a comparison through `string::lowercase(...)`, since SurrealQL has no
  case-insensitive operator of its own.
- **`include` composes with `fetch` and `select`,** narrowing a relation
  load's projection or filtering which to-many records come back, up to two
  levels deep.

## The repository layer

`db.orm` compiles every call to exactly one `SurrealQueryPlan` — the lane-level
guarantee [ADR 003](../adrs/ADR%20003%20-%20One%20Query%20One%20Statement.md)
holds SurrealDB to the same as every other family. Some user-facing
operations genuinely need more than one statement to answer correctly: a
nested create across tables, a reverse relation load, a cascade delete a
target doesn't enforce itself. `@internal/surreal-orm-client` is layer 6 per
[ADR 164](../adrs/ADR%20164%20-%20Repository%20Layer.md) — a place above the
lane, explicitly permitted to orchestrate a sequence of single-statement lane
plans per call, so the lane itself never has to bend its own rule.
`orm({ runtime, context })` returns one repository per declared table, flat
and table-keyed like `SurrealOrm` itself, with a `findMany` / `findFirst` /
`findUnique` / `count` / `findFirstOrThrow` / `findUniqueOrThrow` / `create` /
`update` / `delete` / `upsert` / `groupBy` / `aggregate` /
`manyToManyStrategy` surface per table.

Every strategy this layer picks is read off `contract.capabilities`
([ADR 031](../adrs/ADR%2031%20-%20Adapter%20capability%20discovery%20&%20negotiation.md)) —
`surrealdb.createReturnsRecord`, `surrealdb.upsertByRecordId`,
`surrealdb.referenceOnDelete`, `surrealdb.graphEdges`, and
`surreal.upsertByUniqueIndex` — never a target name. A capability the
contract doesn't declare reads as "not supported" and the call throws a
structured `OrmClientCapabilityError`; there is no silent downgrade to a
different strategy.

**Cascade arbitration** is the one place this layer's behavior runs opposite
to a SQL-shaped instinct. When the contract declares
`surrealdb.referenceOnDelete`, the engine already enforces every declared
`REFERENCE ON DELETE` action as part of its own `DELETE`, so `delete` never
orchestrates anything on top of that. When the capability is absent,
`delete` reads the table's declared `cascade` references and orchestrates
the dependent deletes itself, folded into the same atomic `runtime.batch` as
the primary delete. Only `cascade` is ever orchestrated this way — `reject`
and `ignore` are engine-only semantics this client never emulates, `unset`
likewise, and `then` carries an arbitrary SurrealQL expression this client
does not interpret; all four are left entirely to the engine, capability or
not.

**Nested writes** go one level deep, over both declared record links and
graph-edge (`RELATE`) relations. Every id involved — the parent's and every
child's — is pre-allocated client-side as a `RecordId` before anything
dispatches, so the parent plan, every child `create`, and every `RELATE`
plan can all go out together in one `runtime.batch`: one atomic round trip
regardless of how many nested rows are involved. A relation is named by its
field name for an outgoing link, or by the `"<childTable>.<fieldName>"`
composite for an incoming one, with a bare-table-name shortcut that throws
naming the competing fields when it would be ambiguous. A child payload that
itself carries a `relations` key is rejected — nesting stops at depth 1.

**Reverse and to-many relation loading** — `findMany({ relations: { <key>: true } })` —
is always exactly two round trips, regardless of how many parent rows match:
the parent query itself, then one `runtime.batch` bundling every relation's
queries for every parent. A link-shaped relation becomes one `findMany`
keyed by `{ [field]: { in: parentIds } }` — a single statement no matter how
many parents there are, avoiding N+1 — while an edge-shaped relation becomes
one `traverse` per parent, all still riding inside that same one batch call.

**Telemetry** is opt-in via `onOperationStats` on `orm()`, reporting
`{ table, operation, statementCount, roundTripCount }` once per call that
reaches a dispatch. `statementCount` counts every individual statement,
including each one folded into a batch; `roundTripCount` counts network
round trips, where one `runtime.batch` call is one round trip no matter how
many statements it carries — a nested `create` with three children is 4
statements and 1 round trip.

**Atomicity has two documented gaps**, both a consequence of `runtime.batch`
being unable to branch on an intermediate result: `upsert`'s fallback for a
`where` that names no declared unique index is `findFirst` then
`update`/`create` — two round trips, not a batch, and not atomic, so a
concurrent writer matching the same `where` between the two calls can race
it into a duplicate `create` or a lost update. Similarly, a `where`-based
cascade delete first resolves which ids `where` currently matches via a
plain read, separate from the batch that deletes them and their dependents;
a parent row created between that read and the batch is reflected in
neither. A delete by `id` has no such gap, since it already knows its target
and dispatches everything in one batch with no preceding read.

**`create()` allocates a sequence-backed id via `idFrom`**, mutually exclusive
with `id` — verified against a live SurrealDB v3.2.4. `idFrom: { sequence:
'person_seq' }` compiles to two statements and two round trips: `RETURN
sequence::nextval($seq)` allocates the value, then `CREATE` uses it, both
tagged `meta.lane = 'orm-client'` like every other plan this package
dispatches. It is not atomic — the allocation and the create are separate
round trips, so a crash between them burns a sequence value, which is ordinary
sequence behavior rather than a defect. Telemetry reports `statementCount: 2,
roundTripCount: 2`. The feature is capability-gated on `surrealdb.sequences`;
a missing capability throws `OrmClientCapabilityError` naming it, and passing
both `id` and `idFrom` throws naming both. Two successive creates against a
live server produced `seq_item:0` then `seq_item:1` — distinct and
monotonically increasing.

This lives here, as a multi-statement orchestration, because that is exactly
what layer 6 exists for — per
[ADR 164](../adrs/ADR%20164%20-%20Repository%20Layer.md) — there is no
schema-level substitute to fall back to.
A sequence-backed *field default* works entirely server-side, with no client
involvement: `DEFINE FIELD n ON t TYPE int DEFAULT sequence::nextval("s")`
allocates `0, 1, 2, …` on every `CREATE` that omits the field. A
sequence-allocated *id* can't be reached the same way — `DEFINE FIELD id ON t
VALUE type::record(...)` is silently ignored by the server, and ids stay
randomly generated regardless. The sequence itself must already exist in the
database (`DEFINE SEQUENCE`); this layer allocates from it but has no way to
declare one, and the contract has no representation for a sequence definition.

## Errors are prose

SurrealDB reports failures as English, with no code to switch on. A uniqueness
violation is:

```
Database index `person_name_uq` already contains 'ada', with record `person:1k9…`
```

`classifySurrealFailure` matches the exact message wording SurrealDB v3.2.4
emits — each pattern commented with a sample of it — onto an actionable
`SurrealFailureClass`. Anything unrecognised classifies as `unknown` rather
than being guessed at.

## Identifying a record

Anything that takes a record id accepts the key as text or a number, or a
whole `RecordId`. The last form matters because reads produce one: `row.id`
comes back as a `RecordId`, so feeding it straight back into `findUnique`,
`update` or `delete` has to work without the caller taking it apart.

A `RecordId` from the wrong table is refused rather than silently addressing
another table's row. A complex key — an array or an object — has no identifier
spelling, so it is routed through `type::record`, which takes the key as a
value.

## Decoding a record link

A `record<person>` field arrives as the string `"person:alice"` normally, and
as a nested object once the query says `FETCH author` — the same field, the
same declared type, two wire shapes. The `link` result shape therefore carries
both the codec that parses the id and the record shape to use when the link
was fetched, and the decoder chooses per value.

`NONE` and `NULL` both serialize to JSON `null`, so an absent field and an
explicitly empty one are indistinguishable on the way out. Neither is passed
to a codec.

## DDL

`renderCreateTableStatements` returns a list in dependency order — table, then
fields, then indexes — because an index over a field SurrealDB has not been
told about yet is rejected, and because the migration runner reports progress
per statement.

Three v3 keyword rules, with the server behavior that pins each:

| Rule | Evidence |
| --- | --- |
| `FLEXIBLE` follows `TYPE` | *Parse error: FLEXIBLE must be specified after TYPE* |
| Full-text is `FULLTEXT` | the `SEARCH` keyword no longer parses |
| M-Tree is gone | only `HNSW` remains for vector indexes |

**Trust boundary:** a contract's expression fields — `asSelect`, a field's
`defaultExpression` / `valueExpression` / `assertExpression`, permissions, and
`REFERENCE ON DELETE THEN` bodies — are SurrealQL source held verbatim, by
design, exactly like a raw `CHECK` body in SQL. The DDL renderer splices them
into `DEFINE` statements without inspection, so applying a `contract.json`
executes whatever SurrealQL those fields contain. Only apply contracts you
authored or trust; a contract fetched from an untrusted source is code, not
data. Application *values* never take this path — they are always bound
parameters.

### Referential actions on record links

A `record<>` field can declare what happens to the referencing record when
the record it points at is deleted. `contract-ts` exposes this as
`onDelete` on the field definition — `'reject' | 'ignore' | 'cascade' |
'unset'` — and `schema.prisma` exposes it as `@relation(onDelete: Cascade |
SetNull | Restrict | NoAction)`, mapped respectively onto `cascade`,
`unset`, `reject`, and `ignore`. Both surfaces produce the same
`SurrealReferenceAction` the field carries internally; a fifth kind, `then`,
carries a raw SurrealQL `expression` instead of a fixed keyword, and has no
PSL spelling since PSL has no syntax for an arbitrary follow-up statement.

The renderer emits it as one more clause in the field's `DEFINE FIELD`
statement, right after `FLEXIBLE` and before `DEFAULT`:
`REFERENCE ON DELETE REJECT` / `IGNORE` / `CASCADE` / `UNSET`, or
`REFERENCE ON DELETE THEN <expression>` for the `then` kind. There is no
`SETNULL` keyword in SurrealQL — `SetNull` is the Prisma-facing spelling for
what SurrealDB itself calls `UNSET`.

`SetNull`/`unset` only makes sense on a link that can legally hold nothing:
SurrealDB accepts `REFERENCE ON DELETE UNSET` on a required link at `DEFINE`
time but rejects the delete itself once it actually has to clear that link,
which would make the schema a trap rather than a guarantee. Both authoring
surfaces catch this before it reaches the database — the PSL interpreter
diagnoses a `SetNull` on a non-optional relation field, and contract
validation independently rejects an `unset` reference whose field type isn't
`option<…>`, `array<…>`, or a `set<…>` — so the same mistake can't slip
through a contract authored directly in TypeScript either.

## Schema drift

SurrealDB does not store the DDL it was given: it stores a parsed definition
and re-renders it in its own canonical form. A differ comparing raw text would
report drift on a database it had just created — forever, on every table.

`@internal/surreal-schema-ir` canonicalizes both sides first. Seven
normalizations, straight from how v3.2.4 echoes definitions back:

| Written | Echoed back |
| --- | --- |
| `` DEFINE TABLE `person` `` | `DEFINE TABLE person` |
| `DEFINE FIELD x ON TABLE t` | `DEFINE FIELD x ON t` |
| *(nothing)* | `PERMISSIONS NONE` / `PERMISSIONS FULL` |
| `TYPE option<decimal>` | `TYPE none \| decimal` |
| `TOKENIZERS blank,class` | `TOKENIZERS BLANK,CLASS` |
| `BM25` | `BM25(1.2,0.75)` |
| `HNSW DIMENSION 3 DIST COSINE` | `… TYPE F32 EFC 150 M 12 M0 24 LM 0.402…f` |

An eighth is structural: declaring an `array<float>` field makes SurrealDB add
a `<field>.*` child on its own, which the differ must neither report as
undeclared nor try to remove.

Removals are opt-in. A contract is not required to describe every table in a
database it shares, and dropping an unrecognised table is the one operation
here that destroys data.

A `REFERENCE ON DELETE …` clause is one more part of the field's definition
string, so a hand-changed reference action is caught by this same
canonicalized text diff — there is no separate mechanism for it.

## The control plane

`surrealFamilyDescriptor` registers the family with the framework's control
stack; `@internal/target-surrealdb/control` supplies the contract serializer
and the contract-to-schema projection.

The control-plane adapter itself does none of this work. SurrealDB's control
plane needs no dialect lowering of its own — the DDL above is rendered by
the target from contract IR, and the control driver sends it verbatim — so
the adapter exists only because the framework requires one per target, not
because there is anything for it to do. Its own source states the choice
directly: "it carries no behaviour rather than pretending to."

Two tables live in the user's database. `_prisma_contract_marker` records
which contract it is running, one row per contract space with the space as the
record id. `_prisma_migration_ledger` is the append-only journal of applied
migrations. Both are schemafull and prefixed, and introspection filters them
out — a contract never declares them, so leaving them in would make every
introspection report two tables of drift.

`verify` checks in order: the target matches, a marker exists, the marker's
hash matches the contract, and the live schema matches. Each failure carries
its own code, so a caller can distinguish "never initialised" from "migrated
to a different contract" from "changed by hand".

## Testing

Unit suites assert what the lowerer and the DDL renderer produce. A live suite
asserts that SurrealDB accepts it, covering graph `RELATE` with traversal in
both directions, KNN over an HNSW index, transaction isolation with rollback,
and an injection attempt against the real parser.

Both layers matter. SurrealQL rejected several shapes that looked entirely
reasonable on paper, and only a real server catches that class of mistake.

```bash
docker compose --profile surrealdb up -d   # SurrealDB on :8112, not :8000
pnpm --filter '@internal/*surreal*' test
```

The live suites skip themselves when SurrealDB is unreachable.

## Using it

```ts
// contract.ts — author the schema in TypeScript
import { defineContract, index, relation, t } from '@prisma/orm-surrealdb/contract-builder';

export const contract = defineContract({
  tables: {
    person: {
      fields: { name: { type: t.string() }, balance: { type: t.option(t.decimal()) } },
      indexes: { person_name_uq: { fields: ['name'], variant: index.unique() } },
    },
    follows: { schemafull: false, type: relation(['person'], ['person']) },
    doc: {
      fields: { body: { type: t.string() }, embedding: { type: t.array(t.float()) } },
      indexes: { doc_vec: { fields: ['embedding'], variant: index.hnsw(1536, { distance: 'cosine' }) } },
    },
  },
});
```

```ts
// prisma.config.ts
import { defineConfig } from '@prisma/orm-surrealdb/config';

// wss: in production; the plaintext ws: scheme belongs to local development
// only. The driver accepts exactly these two schemes and rejects the rest.
export default defineConfig({
  connection: 'wss://root:root@db.example.internal/rpc/app/main',
});
```

```ts
import surrealdb from '@prisma/orm-surrealdb';
import contractJson from './contract.json' with { type: 'json' };

await using db = surrealdb({ contractJson, url, namespace, database, username, password });
await db.connect();

// The collection lane.
await db.execute(db.orm.person.create({ data: { name: 'ada', age: 36 } }));
for await (const row of db.query(db.orm.person.findMany({ where: { age: { gte: 18 } } }))) {
  console.log(row);
}

// Or SurrealQL directly. Interpolations are always bound, never spliced.
const name = 'ada';
for await (const row of db.query(db.surql`SELECT * FROM person WHERE name = ${name}`)) {
  console.log(row);
}
```

## Not yet built

- **The migration planner and runner.** The control plane can say what differs
  (`verify`, `verifySchema`) and record agreement (`sign`), and the schema
  differ already emits the operations that would close a gap, but nothing yet
  turns those into an ordered, reviewable migration and applies it.
- **Row-level type inference in the collection lane.** Table names are typed
  off the contract, so `db.orm.persno` is a compile error, but a row is
  `Record<string, unknown>` until the emitted `contract.d.ts` type maps are
  threaded through.
- **Subscription recovery.** A live query does not survive a reconnect —
  SurrealDB drops every one when the socket closes, and re-registering
  silently would replay neither the missed notifications nor the caller's
  intent. A caller that needs continuity has to re-subscribe and reconcile.
